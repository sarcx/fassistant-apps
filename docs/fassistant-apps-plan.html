Building fassistant-apps

One screen listing every Fassistant app, with install and update in the row. Seven milestones, and one certificate problem that has to be solved before anything else is worth writing.

What. A sideloaded Android app whose only job is to show what exists in the Fassistant family and get it onto the phone. Each row is one app: its name, the version installed against the version released, and a single button that says Install, Update or Open. No more hunting through GitHub for a release page.

How. Nothing new has to be invented, because every Fassistant repo already publishes exactly the file this needs. Each one cuts a single release carrying its APK and an update.json naming the version and checksum, at an address that never changes. The catalogue asks GitHub which of your repos carry the topic fassistant, reads one manifest per repo, and compares each against what is installed. Adding an app to the catalogue is therefore one command: tag the repo.

The one real obstacle is a root certificate, and it is already confirmed. GitHub serves release files from a host whose certificate chains to ISRG Root X1. That root shipped in Android 7.1.1 and is absent from Android 7.0 — checked against the AOSP trust store for both releases, not recalled. On a 7.0 phone the app would list everything and then fail every single download. The fix is small and known: ship the root inside the APK as an extra trust anchor, which Android has supported from exactly the API level this app targets. It is milestone 1 because everything else is pointless if downloads do not work.

Kotlin, zero deps minSdk 24 No GitHub token needed Android 7.0 needs a bundled root CA

What the app actually does, end to end

Worth seeing the whole path first, because it explains why the app is small: there is one network call for discovery, one small file per app, and one comparison. Everything else is a list row.

The certificate problem confirmed

This is the finding that shapes the build, so it goes before the stack discussion. GitHub does not serve everything from one place. The listing and the redirect come from github.com; the actual bytes come from a separate asset host. Those two hosts do not use the same certificate authority, and only one of the two roots is present on Android 7.0.

The file names under the certificates are how Android stores its trust store — each root sits in a file named after a hash of its subject. Checking whether a given root is present on a given Android release is therefore a matter of looking for the right filename in that release’s AOSP tree, which is what the table below reports.

Root certificate Store file Android 7.0 Android 7.1.1 Needed for
USERTrust ECC Certification Authority 04f60c28.0 present present The repo listing and every redirect
ISRG Root X1 the problem 6187b673.0 absent present Every manifest and APK download
DigiCert Global Root G2 c90bc37d.0 present present Nothing today — GitHub has moved off it
Checked directly against the AOSP system/ca-certificates tree at tags android-7.0.0_r1 and android-7.1.1_r1, and against the live certificate chains served by both hosts.

The fix, and why it is cheap

Android 7.0 introduced per-app network security configuration, which is the same API level this app targets. That is a lucky alignment: the app can declare its own trust anchors in a small XML file, listing the system store and one root shipped inside the APK. The root certificate is about 1.4 KB. Nothing else in the app changes, and on 7.1.1 and later the bundled copy is simply redundant.

<network-security-config>
  <domain-config>
    <!-- GitHub serves release assets from a host whose chain ends at ISRG Root X1,
         which Android only started shipping in 7.1.1. On 7.0 the system store cannot
         verify it, so the root travels with the app. -->
    <domain includeSubdomains="true">githubusercontent.com</domain>
    <trust-anchors>
      <certificates src="system" />
      <certificates src="@raw/isrg_root_x1" />
    </trust-anchors>
  </domain-config>
</network-security-config>

app/src/main/res/xml/network_security_config.xml — proposed

This affects the two existing apps too. Both download their own updates from the same asset host — app/src/main/kotlin/dev/todor/fassistant/update/UpdateChecker.kt:66 — and fassistant-android declares minSdk 23. On any phone running Android 7.0 or older, self-update has never been able to work and would have failed with a certificate error rather than anything that names the real cause. The same one-file change fixes it in both repos.

Stack

The interesting decision is not the language — matching the two sibling repos is obviously right — it is how the app finds out which apps exist. You have already picked topic-based discovery; the table records what the alternatives cost, so the choice stays legible later.

One small change to the family’s manifest

A row cannot say “installed 0.4.1, latest 0.5.0” without knowing which package on the phone belongs to which repo, and today’s update.json does not say. Two fields close that, written by the same dist task that already writes the rest.

File(target, "update.json").writeText(
    """
    {
      "versionCode": $appVersionCode,
      "versionName": "$appVersionName",
      "apkUrl": "fassistant.apk",
      "sha256": "$digest",
      "packageName": "${android.defaultConfig.applicationId}",
      "label": "Fassistant",
      "notes": "${jsonEscape(releaseNotes(changelog))}"
    }
    """.trimIndent() + "\n"
)

fassistant-android/app/build.gradle.kts:124 — the two highlighted lines are the change

The catalogue must not require them, because both existing releases predate this plan. A manifest with no packageName still gets a row and an Install button; what it loses is the ability to say whether the app is already on the phone. That degradation disappears the first time each repo cuts a release.

Milestones

Ordered so the two things that could still go wrong are settled first: whether downloads work on the oldest phone, and whether discovery by topic behaves as documented. Each one runs on a real phone before the next starts.

The phones are never plugged into anything, and none of them are rooted. That rules out the usual ways of finding things out, and it changes three milestones. Publishing a release is the only way anything reaches a phone, so the release workflow is not the last step — it had to be built first, and it was. Anything the app needs to tell us has to appear on its own screen and be sendable from there, because there is no log to read. And the permission that lets the app install apps has to be explained and linked to in the app itself: granting it over a cable is not available.

1

Download something on the oldest phone built, awaiting the phone

A bare app, minSdk 24, one button. It fetches a real update.json from the live release URL and then the APK it names, and checks what it got against the published checksum.

Whether the bundled root is doing any work is answered in the same run rather than by building twice: the app constructs both sets of trust anchors itself — the phone’s own certificates, and those plus the root in the APK — and puts the same fetch through each. One install answers it, which matters when installing means publishing a release and opening a link on the phone.

ProofThe 0.5.0 APK lands on the phone and its checksum matches 9f2ec955… from the published manifest — already confirmed against the live release from a laptop, so a failure on the phone is the phone talking. The screen then says either “this phone needs the bundled root” or “this phone would have managed without it”, and a button sends the whole report off the device.
2

Discovery by topic

Tag fassistant-android with the topic, then have the app call the repo listing, keep the tagged repos, and read one manifest each. No interface yet — this is a log line per app. Cache the parsed list on disk so a rate-limited or offline launch still shows something.

ProofThe app logs one app. Tag a second repo, refresh, and it logs two, with nothing rebuilt and no file edited. In aeroplane mode it still logs the list it saw last time.
3

Add the two manifest fields

Extend the dist task in fassistant-android and fassistant-click to write packageName and label, and make the catalogue treat both as optional. Cut a release of each so the published manifests carry them.

ProofThe published update.json for both apps contains the new fields, and the catalogue reports an installed version for one and “not installed” for the other, correctly, on a phone where only one is present.
4

The list screen

The app as you would actually look at it: one row per app with its name, the installed version against the latest, a state pill, and one button whose label matches the state. Icons come from PackageManager for installed apps and a letter tile for the rest. Pull to refresh; tap a row to expand the release notes.

ProofOn a phone with the watchdog installed at 0.4.1 and the auto-clicker absent, the screen reads “Update to 0.5.0” and “Install 0.1.0” without being told anything by hand.
5

Install and update

A PackageInstaller session per app, with the checksum and signing certificate both verified before the system prompt appears — the same two gates the existing self-update already applies at UpdateChecker.kt:81, which work across apps precisely because the whole family is signed with one key. Plus a single action that updates everything that is out of date, one prompt at a time.

ProofInstall puts an absent app on the phone. Update replaces an installed one in place, with no uninstall step and its data intact. A deliberately corrupted manifest checksum stops the install before any prompt is shown.
6

The unknown-sources gate two different settings

Installing from an app requires permission to install apps, nothing explains that on a fresh phone, and with no cable it cannot be granted from a laptop. So the app has to walk the user there itself — and where “there” is depends on the Android version, which is easy to get wrong because the two look nothing alike.

On Android 7 the setting is a single global switch covering every app on the phone. On Android 8 and later it is granted per app, and there is a settings screen belonging to this app specifically. A screen that only handles the newer case would send a 7.0 phone — the one this whole plan is shaped around — somewhere that does not exist.

ProofOn a phone that has never granted it, the screen says so and its link opens the right settings page for that Android version. After granting it by hand, the same screen reports the gate open and an install goes straight to the system prompt.
7

Release it like the others brought forward, done

This was meant to be the last step and became the first, because a release is the only way anything reaches a phone. The version lives in gradle.properties, the dist task builds the APK and its manifest, and the release workflow follows fassistant-android's. Confirmed locally: the signed build carries the same certificate as the published watchdog, which is what lets the catalogue tell a real Fassistant release from anything else.

What is left for the end is the part that depends on the app existing: tagging this repository fassistant, so the catalogue lists and updates itself.

ProofPushing the tag v0.1.0 produces a release carrying both assets, and the catalogue running on the phone shows itself as a row and can update itself from it.

Open questions

Which Android 7 is the phone actually running?

It decides whether the bundled root is load-bearing or merely insurance. 7.0 and 7.1.1 are both “Android 7” in conversation and differ on exactly the certificate this app depends on.

Recommendation: ship the bundled root either way — that part is settled, since it costs about 1.4 KB and covers whatever old phone turns up next. The question is now the app's to answer rather than yours: the check screen reports which Android the phone runs, whether its own certificates include that root, and whether the download would have worked without help.

Should the same certificate fix go into the two existing apps?

Their self-update downloads from the same host, so on Android 7.0 and older it has never been able to work.

Recommendation: yes, as a small separate change in each repo rather than something bundled into this project. It is the same file, and it is a real bug sitting in shipped code.

Does fassistant-click get pushed to GitHub?

It has no remote at the moment, so it has no releases and cannot appear in the catalogue. Without it the app ships with exactly one row in it.

Recommendation: push it and tag v0.1.0. Its release workflow and dist task are already written and its dist/ directory already holds a built APK and manifest, so this is the push and the tag, nothing more.

Icons for apps that are not installed yet

An app’s icon lives inside its APK, so there is nothing to show before it is on the phone short of downloading the APK to look.

Recommendation: a letter tile until installed, the real icon afterwards. If it bothers you later, an iconUrl in the release manifest is an easy addition — but it is another field for every repo to maintain, for a row you look at once.

Should the catalogue check for updates on its own?

The plan has it refresh when opened or pulled. Background checks would mean a scheduled job and a notification, which is a meaningful amount of the machinery the watchdog app exists to contain.

Recommendation: leave it manual for 0.1.0. It is a screen you open when you want to install something; a daily check that notifies you is a separate feature worth deciding on once the app exists.

Assumptions

Everything decided rather than asked
  • Owner and visibility. Repos live under sarcx and stay public, so no token, no login screen, and nothing secret in the APK. Taken from the existing remote and your answer.
  • New repo, same family. sarcx/fassistant-apps, application id dev.todor.fassistantapps — matching how fassistant-click names itself, rather than sitting underneath the watchdog's own package. Signed with the existing key at ~/Sites/.fassistant-signing/fassistant.jks. The shared key is not incidental: it is what lets the catalogue reject a download whose signature does not match the family before showing you a prompt.
  • Discovery endpoint. The public repo listing for a user, unauthenticated, one request per refresh. Topics come back in that response without any extra header — verified against the live API.
  • minSdk 24, targetSdk 25. 24 because you asked for Android 7, and it happens to be the first release with per-app network security config. 25 for the same reasons the sibling repos give, plus package visibility.
  • No AndroidX, no layout XML. Both sibling repos set android.useAndroidX=false and build every view in Kotlin; neither has a res/layout directory at all. This one matches.
  • Offline behaviour. The parsed list is cached on disk and shown when GitHub cannot be reached, with the age of the cache visible rather than hidden.
  • No root, and no cable. Nothing assumes either. Installing goes through PackageInstaller, which is the route available to an ordinary app, and every answer the app needs to give has to be readable and sendable from its own screen.
  • Not in scope. Uninstalling, any app outside the family, private repositories, and background update checks.

Every certificate chain, trust-store entry, API response and file reference in this document was checked against the live services and the repositories at ~/Sites/fassistant-android and ~/Sites/fassistant-click. Nothing here is written yet.
